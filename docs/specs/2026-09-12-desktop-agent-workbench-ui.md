# 阶段七：桌面 Agent 工作台与 UI

**状态：** Draft

**日期：** 2026-09-12

**所属阶段：** 阶段 7——桌面集成（尚未开始）

## 目的

把前期桌面 UI 讨论收束为一份可审阅、可拆分、可验证的阶段七输入，避免在 Logo、视觉风格、前端框架和桌面架构之间相互锁死。

本规格只描述桌面端应呈现的产品体验、信息架构和 Core 事实映射。它不启动阶段七，不授权添加 Electron 依赖或桌面代码。

## 本次校准结论

### 已确认

- Vera 的最终形态是桌面 Coding Agent；CLI 是内部 Core 开发、验收和产品化载体。
- 阶段七首个桌面底版采用 Electron，继续使用独立 Python Core 和版本化 `Command -> VeraRuntime -> Event` 契约，见 [ADR-0013](../decisions/ADR-0013-electron-desktop-baseline.md)。
- 桌面端不得解析 CLI/TUI 文本，不得复制 Runtime、Policy、Approval、Checkpoint、Verification 或 Recovery 逻辑。
- 阶段七入口门禁不变：阶段五 Complete、阶段六 Complete，且用户明确确认「CLI 版本达到预期，可以封存」。

### 推荐基线，待用户确认

- 产品形态采用“Agent 工作台”，而不是纯聊天窗口，也不是完整 IDE。
- 默认布局由左侧导航、中央任务时间线、右侧证据检查器和底部输入区组成。
- 界面首先让用户理解“Vera 正在做什么、为什么需要我决定、结果有什么证据”，再按需展开技术细节。

### 继续独立决策

- Vera Logo 与品牌视觉系统；
- 前端框架（Vue、React 或其他方案）；
- Electron 与 Python Core 的进程传输、分帧和打包方式；
- 主题、字体、动效、窗口细节和最终视觉稿；
- 安装包、签名、公证、更新、最低系统版本和资源预算。

## 产品定位

Vera 桌面端是“可对话、可监督、可验证、可恢复的本地 Agent 工作台”。它需要同时满足两种使用节奏：

1. 用户可以像对话一样自然提出目标、补充上下文和纠正方向；
2. 当 Agent 读取文件、运行命令、申请批准、产生 Diff、执行验证或需要恢复时，用户可以看到结构化事实并做出明确决定。

桌面端不以代码编辑器为中心。需要查看代码时提供聚焦的文件、Diff、命令输出和证据视图；完整编辑器、LSP 和 IDE 面板不属于本阶段范围。

## 设计参照原则

- 借鉴成熟对话产品的低学习成本与自然输入体验；
- 借鉴 Coding Agent 产品对工具过程、Diff、批准和验证的显式展示；
- 借鉴任务管理产品清晰、稳定、克制的信息层级；
- 只吸收交互原则，不复制某个产品的布局、品牌或视觉语言。

## 信息架构

以下结构是推荐基线，规格接受前仍可调整。

### 左侧：工作区与任务导航

- 当前本地工作区及其边界；
- 任务或会话列表、状态和最近活动；
- 新建任务、切换任务和恢复历史任务的入口；
- 不把实现细节、工具列表或设置长期挤占主视区。

### 中央：对话与运行时间线

- 用户目标、补充信息和 Vera 回复；
- 按真实顺序出现的工具活动、状态变化和阶段性结果；
- 运行中、等待批准、验证中、已完成、已取消、失败和可恢复状态；
- 默认展示摘要，允许展开原始参数、输出和关联文件。

中央区是视觉主轴。任何侧栏都必须可折叠或调整宽度，不能让主对话和任务证据失去可读空间。

### 右侧：证据检查器

- 文件与 Change Set；
- Diff、验证结果、命令证据和失败原因；
- 批准范围、策略结果、内容来源和风险提示；
- Checkpoint、恢复与回滚事实。

右侧面板随中央时间线中的选中对象切换，不制造第二套状态，不把尚未发生的动作显示为已完成。

### 底部：输入与任务控制

- 自然语言输入、附件或上下文入口；
- 清楚区分发送消息、开始执行、停止或取消；
- 当任务等待用户决定时，把当前决定放在输入区附近，但不以模糊的默认按钮代替明确批准。

## 核心用户流程

1. 用户选择或确认工作区，看到 Vera 的访问边界与当前状态。
2. 用户描述目标；Vera 通过同一 Core 契约建立或继续任务。
3. 中央时间线持续呈现对话、工具活动和状态，长输出以摘要加按需展开呈现。
4. 需要授权时，界面展示具体动作、目标、参数、风险、来源和批准有效范围。
5. 产生修改后，用户在证据检查器查看 Change Set 与 Diff。
6. Vera 展示独立验证结果；失败时说明失败事实、可重试动作和是否存在恢复点。
7. 完成态同时包含结果摘要、实际变更、验证证据和下一步，不以模型文字单独宣告成功。

## Core 事实与 UI 表面

| Core 事实 | 默认 UI 表面 | 约束 |
| --- | --- | --- |
| 对话输出 | 中央消息 | 与运行状态分离，不伪装成工具事实 |
| 工具活动 | 时间线事件卡 | 显示真实状态；参数与输出可展开 |
| Change Set / Diff | 右侧检查器 | 只展示 Core 权威内容，不在 Renderer 重新推断 |
| Approval | 时间线与输入区附近的决定卡 | 绑定具体动作和参数，不提供含糊的永久授权 |
| Verification | 证据检查器与完成摘要 | 区分通过、失败、未运行和被阻断 |
| Policy / provenance / risk | 对应事件和批准卡 | 风险不能只靠颜色表达；不可信内容不能授予权限 |
| Checkpoint / recovery | 状态条与证据检查器 | 只展示实际可恢复状态，不承诺不存在的恢复能力 |
| Error / cancellation | 时间线与任务状态 | 给出影响范围、保留状态和可采取的下一步 |

## 交互与安全原则

- **事实优先：** UI 只解释 Core 事实，不自行判定成功、授权、风险或恢复结果。
- **渐进披露：** 普通用户先看到结论和下一步；需要审查时能追溯参数、输出、Diff 和日志。
- **批准可理解：** 每次批准明确回答“要做什么、在哪里做、为什么、影响什么、批准到何时”。
- **状态不只靠颜色：** 使用文字、图标和结构共同表达；支持键盘操作、清晰焦点和可读对比度。
- **敏感信息最小化：** 默认不展示凭据和被脱敏内容；复制、展开和导出仍遵循 Core 边界。
- **Renderer 最小权限：** 无 Node.js、文件系统、Shell、凭据或 Core 进程直连能力，只使用窄化 Preload API。
- **失败可恢复：** 崩溃、断连、取消和验证失败必须显示已知状态，不能让“界面消失”等同于“任务已结束”。
- **桌面与 CLI 语义一致：** 两者共享状态、审批、错误与恢复概念，但不要求布局和表现形式相同。

## 视觉与品牌约束

Logo 作为独立设计专题继续讨论，不在本规格中定稿，也不阻塞信息架构确认。后续 Logo 系统至少需要覆盖：

- 桌面完整标识与应用图标；
- 小尺寸、单色和菜单栏形态；
- CLI 启动标识；
- Unicode 微标识与纯 ASCII 回退形态；
- 深色、浅色、低色彩和无色环境。

当前可继续探索的语义方向是：以 `V` 的上扬笔画接近或触碰星点，表达科技、人文与星空般的深度。整体应克制、优雅、有辨识度，避免廉价霓虹和只依赖渐变的识别方式。最终造型、颜色、字标与 CLI 图形均需单独评审。

## 阶段七后续增量

以下仅用于重新校准路线，不代表任务已建立或阶段已启动：

1. **7.1 安全桌面壳：** Electron 窗口、受限 Preload、Core 生命周期和结构化传输。
2. **7.2 工作台骨架：** 工作区/任务导航、中央对话与运行时间线、基础状态恢复。
3. **7.3 证据闭环：** Diff、批准、验证、风险、Checkpoint 与 Recovery 检查器。
4. **7.4 产品体验：** 键盘、可访问性、主题、长内容、窗口适配、性能和崩溃路径。
5. **7.5 私有交付：** Python Core 打包、签名、公证、更新、安装与真实 Mac 验收。

每个增量都必须建立独立 Accepted 规格或任务，且复用同一 Core 契约。

## 非目标

- 当前开始 Electron Spike、安装依赖或编写桌面代码；
- 把 Vera 做成完整 IDE、代码编辑器或 LSP 替代品；
- 在桌面 Renderer 中复制 Core 业务、安全或恢复逻辑；
- 引入 Multi-Agent、复杂 RAG、插件市场或云端编辑；
- 在本规格中锁定前端框架、最终 Logo 或完整视觉系统；
- 直接迁移 `/Users/admin/Coding-harness` 原型代码。

## 失败行为

- Core 未启动、断连或协议不兼容时，界面进入明确的不可执行状态，保留可确认的任务事实并提供诊断或重连入口。
- Event 缺失、乱序或无法解码时，不猜测进度，不展示成功态；记录协议错误并阻止需要错误状态继续执行的动作。
- 批准内容不完整、已过期或与当前参数不一致时，必须重新请求批准。
- Diff、验证或恢复证据不可用时，明确标为“不可用”或“未验证”，不能用对话文案补齐。
- 窗口关闭或 Renderer 崩溃不自动等同于取消 Core；主进程必须按已接受的生命周期规则处理并在恢复后显示真实状态。

## 本规格接受条件

本 Draft 可转为 Accepted 的前提：

1. 用户确认或修订“Agent 工作台”产品形态；
2. 用户确认或修订四区信息架构及中央时间线的主次关系；
3. Core 的关键事实均有唯一、可追溯的 UI 表面，且没有在桌面层复制权威逻辑；
4. 已确认、推荐待定和独立决策三类内容没有混写；
5. Logo 被保留为跨桌面与 CLI 的独立设计专题；
6. 阶段七入口门禁和当前阶段状态保持不变。

## 阶段七最终验收方向

- 用户能在桌面端完成选择工作区、提出目标、监督执行、批准动作、审阅 Diff、查看验证和恢复任务的完整闭环；
- 同一场景的桌面与 CLI 使用相同 Command/Event 语义，桌面不解析 CLI 文本；
- 安全、失败、重连、取消和恢复路径均有真实设备证据；
- Electron 的启动时间、空闲内存、安装体积、进程残留和发布维护成本达到阶段七另行接受的预算；
- Renderer 权限边界与 IPC 允许列表通过独立安全验证。
