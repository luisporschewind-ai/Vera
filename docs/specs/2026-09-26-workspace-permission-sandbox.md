# Vera 工作区权限沙盒：首版收敛方案

**状态：** Accepted（2026-09-26 用户确认并授权实施）
**日期：** 2026-09-26
**用户目标：** Vera 在指定文件夹内工作；访问其他文件或目录、联网、使用额外系统权限之前请求批准。以这一行为目标为中心实现，避免过度设计。
**关联：** [原沙盒规格](2026-09-24-core-execution-sandbox.md)、[ADR-0023](../decisions/ADR-0023-runner-first-sandbox-staging.md)、[任务 0087](../tasks/0087-core-sandbox-alternative-backend-probes.md)、[实施拆分 0088](../tasks/0088-core-sandbox-runner-first-execution-plan.md)。

本方案按用户当前确认生效，替代原规格中首版完整 Core/Broker 多层 OS 隔离要求。用户已授权本会话继续实施；不宣称尚未实测的后端能力或改变其他阶段完成状态。

**本轮范围修正：** 用户明确联网能力后期规划。本轮不新增联网工具、域名授权、代理服务或网络审批 UI；项目命令及后代默认禁网，联网请求返回 `sandbox_network_unsupported`，不能通过文件权限审批开启。已有模型服务属于可信 Core 的既有通道，不开放给项目命令。下文联网审批示例仅为后续方向，不属于本轮验收。额外系统能力默认拒绝，不实现系统提权；2026-09-28 用户另行接受了 [Apple iOS 构建系统服务授权边界](2026-09-28-apple-ios-build-service-boundary.md)，仅该具名能力可按其规格经单次命令审批后开放。

## 1. 用户能理解的一条规则

**Vera 只能使用已经授权的资源；需要更多权限时先询问，拒绝后就不能使用。**

用户选择项目目录，就是授予该工作区的日常开发访问权限。有效权限由“基础运行权限 + 当前工作区 + 用户追加授权”组成。目录是文件边界，联网目的地和系统能力是另外两类权限。

| 资源或动作 | 默认行为 | 扩大权限时的行为 |
|---|---|---|
| 已选择的工作区 | 可以读取、搜索、编辑、运行项目命令；危险动作仍走现有 Policy/Approval | 不因在工作区内就豁免删除、发布等既有审批 |
| 工作区外的普通文件/目录 | 不允许读取或写入 | 展示具体路径和只读/读写范围，用户批准后访问 |
| 系统库、选定工具链、必要系统元数据 | 仅开放已说明并获授权的基础运行集合 | 新增工具链或额外系统路径时说明新增范围 |
| 临时文件与构建缓存 | 优先写入 Vera 为本次工作准备的专用目录 | 工具必须写其他位置时，申请那个具体目录 |
| 模型服务 | 使用用户配置并批准的 Provider 通道 | 修改目的地或用途时重新授权；项目命令不继承此权限 |
| 项目命令、依赖下载及其他联网 | 默认拒绝外部连接 | 申请目的地主机和必要端口，批准后才可连接 |
| 本机服务、Unix socket、自动化、设备等能力 | 不随工作区授权开放 | 单独申请；首版后端无法安全提供的能力明确拒绝 |

“只在目录里工作”不等于把当前工作目录设成该路径。绝对路径、`..`、符号链接和项目子进程都不能成为绕过授权的途径。

## 2. 使用流程与审批

1. **打开项目。** 展示当前工作区和基础运行权限摘要。首次使用时由用户确认；相同权限集合不重复询问，工具链范围扩大时重新确认新增部分。
2. **正常工作。** 阅读、修改和运行已授权范围内的项目任务。沿用现有 Diff、文件变更计划、危险动作审批及恢复能力。
3. **需要越界。** 执行前能识别需求就提前询问；命令运行时被 OS 拒绝，则暂停该操作，展示已确认的资源需求。无法准确判断被拒资源时报告具体错误，不猜测并申请整个磁盘或全部网络。
4. **用户决定。** 首版提供“仅本次操作允许”“本次会话允许”“拒绝”。申请卡说明用途、精确资源、权限类型及有效期；目录授权明确是否包含子目录，读权限不自动带写权限。
5. **授权生效。** 文件操作重新检查权限；命令以新权限启动受限执行。不会修改所有正在运行的命令权限。前一次命令可能已有文件或网络副作用时，先核对结果，再决定如何恢复执行，不能盲目整条重跑。

示例：

> 为复用公共组件，需要读取 `/Projects/SharedUI` 及其子目录。
> 权限：只读；不会获得修改权限。
> 选择：仅本次操作允许 / 本次会话允许 / 拒绝。

另一个例子：安装依赖需要访问 `registry.npmjs.org:443`，Vera 申请这个目的地；后续脚本访问另一个域名仍需要授权。首版授权粒度是主机和端口，不声称限制到某个 URL 路径。

会话授权可查看和撤销；撤销时终止使用该授权的执行，再按剩余权限重新开始。重启/恢复会话时，额外会话授权默认失效。首版不提供永久“全部允许”或一键关闭沙盒。

## 3. 基础运行权限怎样保持简单

把程序正常运行必需的权限整理成一份可查看的集合，在初始化时授权，而不是对每次系统库读取弹窗：

- 操作系统运行库、标准命令和选定工具链的只读文件，以及确实必要的系统元数据。
- Vera 自身的安装文件、专用状态和临时目录；这些内部权限不自动传给项目命令。Provider 凭据不放入项目命令的环境或可读文件范围。
- 每个工作区/会话的专用 HOME、临时及缓存目录；优先使用工具支持的参数和环境设置重定向写入。

基础权限中不得包含整个真实用户 home、其他项目、SSH 凭据、浏览器数据或整个 `/private/var`。位于用户 home 内的工具链只申请准确的安装路径，不能顺带开放其父目录。不能拿“工具需要”作为自行扩权的依据。

对 Git/xcrun 等实际需要额外系统资源的工具，先确定具体路径与读写类型；能重定向则使用专用目录，不能重定向则明确申请必要范围。没有合适边界时说明该操作暂不支持，不以关闭沙盒解决。

## 4. 最小技术结构

复用现有 Core 中的 Workspace、Policy、Approval 和进程监督，只补齐统一授权记录与执行适配：

```text
用户选定工作区 / 用户审批
            ↓
Core：统一权限检查与授权记录
            ├─ 内建读取、搜索、编辑 → 受控文件入口
            ├─ 模型及其他内建联网 → 受控网络入口
            └─ Bash / Git / 构建 / 项目脚本
                         ↓
                  OS 沙盒执行入口
                         ↓
                  命令及全部后代
```

- **文件入口：** 所有模型可触发的读取、搜索、编辑、附件访问都检查同一授权。以真实解析后的路径判断范围，处理符号链接与目录替换，不能仅用字符串前缀。实际打开文件时仍需保证授权对象未被替换；工作区外请求在读取内容之前被拦截。
- **命令入口：** 所有 Agent 发起的 OS 命令统一进入沙盒，子进程继承限制；脚本不能直接读取其他项目或绕过代理直连网络。保持现有超时和进程监督，并验证取消后代。项目配置、Skill 和模型输出不能修改后端权限配置。
- **网络入口：** 内建网络工具使用同一授权规则；项目命令由 OS 限制出口，再由代理检查目的地。仅设置代理环境变量不构成边界。模型调用和项目执行的目的地授权、凭据保持分离。
- **系统能力：** Core 审批与 macOS 自身授权均须满足。Vera 内的批准不能替代系统权限。具名的 Apple iOS 构建服务按专门规格申请，不能由普通文件或命令授权推导；无法限定范围的能力仍拒绝，也不把 `sudo`、桌面自动化或 Docker socket 当普通项目命令放行。

首版将 Vera 自身的权限检查代码视为可信组件，不要求把整个 Core、Runner、Broker 分别做成独立的 OS 隔离进程。保护目标是模型和项目内容不能通过 Vera 的功能越权，以及项目执行代码不能越过 OS 边界；**不承诺整个 Core 进程发生任意代码执行漏洞后仍被独立 OS 沙盒兜底**。这是相对原规格明确收窄的保证，产品状态必须如实说明。

Vera 自身的任意直接文件/网络调用不能成为模型可用的旁路。实现前盘点相关入口；内建文件授权和命令 OS 隔离必须共同验收，不能只交付 Bash 限制就宣布本方案完成。

## 5. 后端建议与现有证据

建议继续验证固定版本 Anthropic Sandbox Runtime，macOS 由其 Seatbelt 实现执行限制，Vera 负责授权、配置和生命周期适配。它是后端候选，不是授权决策者；上游默认广泛读取、共享临时目录和可关闭限制的选项不能直接成为 Vera 默认值。

选择这一方向是因为已有可审阅的原生执行实现和文件/网络控制入口。本轮[最小试验](../evals/core-sandbox-srt-minimal-probe-2026-09-26.md)只证明它能启动受限 Shell；严格配置下 Git/xcrun 仍被系统资源访问阻断，边界负例没有执行。它尚未达到可交付结论。

仅用应用层拦截不能约束任意项目脚本，所以仍需 OS 后端；VM 会引入独立开发环境，不作为本方案首版路径。首版聚焦 macOS，Intel 与 Apple Silicon 都须分别验证。Linux 后续；Windows 保留条件性支持，不提前建设三套后端。

## 6. 实施顺序与验收

接受本方案后，按三个小步骤推进。具体进程拆分与类名属于实施选择，不额外成为产品目标。

| 步骤 | 要完成的结果 | 验收依据 |
|---|---|---|
| 1 工作区与审批 | 统一文件/网络授权记录；内建工具的允许、申请、拒绝及会话权限展示 | 目录外读写在访问前被拒绝；批准只读后能读不能写；拒绝后没有内容泄露或写入 |
| 2 命令 OS 隔离 | 在同一授权下运行 Shell 和假项目，验证文件及本机网络限制；接入所有 Agent 命令入口 | 范围内任务成功；后代越界读写、链接越界、绕过代理直连均被拒绝；批准单一资源后仅该资源可用；取消无后代残留 |
| 3 原生开发可用性 | 补齐基础权限与缓存映射，验证 Git、选定工具链和实际项目任务 | 正常任务成功且此前负例保持拒绝；Intel/arm64 分别取得运行证据 |

第二步先验证通用的允许/拒绝/审批闭环，工具链兼容问题在第三步单独处理。无需先让 Xcode 全部可用才验证文件和网络边界；也不能用通用 Shell 成功宣称任意项目都兼容。

三步完成前只标注具体已完成能力。CLI 和未来桌面端共用 Core 契约，不能各自维护权限策略。未运行的架构、平台或系统能力标明不可用，不静默改为宿主无约束执行。

最终验收还须覆盖：工作区内敏感或危险动作保留原有 Policy；内建工具与 Shell 使用同一授权；批准 A 不开放 B；项目文件不能伪造批准；授权过期/撤销不再可用；部分执行后的审批重试不重复副作用；后端初始化失败时命令不启动。资源不足、权限拒绝和后端不可用应能区分。

## 7. 对原方案的收敛

| 原要求 | 本方案建议 |
|---|---|
| 完整 Core、独立 Broker、更窄 Runner 三层分别 OS 隔离作为最终前置门槛 | 首版采用可信 Core 统一授权 + 命令树 OS 隔离；更强的 Core 失陷隔离另行评估 |
| 项目命令默认只读源码，仅写逐动作产物目录 | 用户选择工作区时授权日常开发读写；危险动作和现有文件变更规则继续保留 |
| 每条命令重新发现所有系统资源，反复验证最小白名单 | 建立经过审阅的基础运行权限和已选工具链集合；仅新增范围需要申请 |
| 账户、XPC、VM 等多条宿主架构并行推进 | 聚焦一个现成原生后端候选，围绕实际权限闭环验证 |
| 后端选型受完整多层隔离、全部工具链和所有安装形态一同阻塞 | 按工作区审批、命令边界、原生兼容三个步骤获取证据；发布声明仍取决于真实覆盖范围 |

本次修订不增加账户体系、VM 管理、权限 DSL、永久授权策略平台或新的桌面实现。保留工作区边界、明确审批、凭据保护、后代继承和失败关闭这些直接实现用户目标的要求。
