## 目标

Vera 可以在用户明确选择的工程中调查、编辑、运行工具、验证和恢复，同时由操作系统限制 Core 与项目代码对本机其他数据和资源的访问。沙盒是 Core 的执行边界，不能要求项目属于预置语言、框架或工程类型。具体平台若无法提供承诺的隔离能力，Vera 必须报告能力缺口并拒绝以“已受沙盒保护”的名义执行。

Vera 的长期目标是成为可开源、可让他人放心使用的通用 Coding Agent。可信任意味着用户能预期 Vera 会做什么、看清它实际获得了什么权限、在失败后恢复，并能独立核查安全声明。沙盒是这一目标的必要组成部分，但不能单凭“已启用沙盒”标签替代真实行为、证据和局限说明。

本规格与现有 Workspace、PolicyEngine、ApprovalGate、ToolExecutor、Checkpoint、Recovery、Event/Journal 叠加，并遵循[产品定义中的 Core 能力与产品形态边界](../PRODUCT.md#core-能力与产品形态)。应用层策略决定动作是否符合用户目标；OS 边界限制获得授权的进程实际能接触什么。两层的通过结果不能互相替代。

## 当前基线与约束

- 当前 `ProcessSupervisor` 提供结构化 argv、`shell=False`、环境过滤、进程组取消、超时和有界输出；`/status` 仍报告 `current user · no OS sandbox`。这些是进程管理与应用层限制，不是 OS 沙盒。
- 阶段八 Tool/Policy/Git 与阶段九 Skills 的 Accepted 契约继续有效。Skill、仓库文件、模型输出和工具输出不能提升权限；原生 Git 与验证仍受各自的计划、审批和恢复约束。
- CLI、Plain、JSON、评测及未来桌面客户端只消费同一 Core Command/Event 事实，不在客户端复制沙盒决策。
- 阶段八和九仍按现有人工验收门槛收口。本规格不修改其状态，也不启动阶段十。

## 威胁模型

需要约束的输入包括模型误判、项目指令与源码中的提示词注入、恶意或被入侵的项目脚本、依赖安装器、构建工具、Git Hook，以及这些进程派生的子进程。需要保护的资源包括未授权的工程与用户文件、Provider 凭据、Vera 私有状态、系统配置和未批准的网络出口。

用户明确授权工程后，工程内普通源码可被读取并按 Policy 修改。用户允许发送给所选 Provider 的上下文会离开本机；沙盒不能承诺阻止这项产品行为。沙盒也不承诺抵御内核漏洞、拥有管理员权限的本机对手，或用户明确批准的外部发布动作。拒绝、审批和明示的能力缺口必须分别呈现。

## 进程与权限边界

```text
CLI / Plain / JSON / 未来桌面客户端
              ↓ 结构化命令与用户批准
可信启动及资源 Broker
              ↓ 有界授权与 IPC
受 OS 隔离的 Vera Core
  Agent / Context / Policy / Approval / ToolExecutor / Recovery
              ↓ 动作级能力
隔离更严格的 Execution Runner
  项目命令 / 验证 / Git 子进程及 Hook
```

1. **完整 Core 入隔离域。** Agent 循环、Context、ToolExecutor、Policy、Approval 与恢复逻辑不能有一部分暗中留在不受限的宿主进程。实现可采用多个受限进程，但对外仍是一个 Core 权威。
2. **Broker 权限最小化。** 宿主侧 Broker 只负责启动、用户授予资源、Provider 凭据与受控网络传输、必要的持久资源访问。它不替模型执行项目命令，不复制 Tool/Policy 业务判断；但必须独立验证 Core 请求是否落在用户授予的能力内，不能把 Core 自报的 `allow` 当作宿主授权。
3. **执行子进程权限更窄。** Agent 发起的结构化 Bash、原生 Git、验证、构建、安装器、项目脚本及 Git Hook，连同所有后代，都通过统一受限执行入口进入 Runner；工具名或是否使用 Shell 不决定隔离范围。Runner 不能直接继承 Core 私有状态、Provider Key、Broker IPC 或 Provider 网络权限。OS 隔离必须覆盖整棵进程树；只收紧环境变量不算达标。
4. **Provider 通道固定目的地。** Core 通过受控接口调用用户配置的 Provider；Broker 不提供任意 URL 请求接口。项目进程默认无网络。依赖下载或其他联网动作需要独立、可见、限期的授权；平台若只能提供比所批准范围更宽的联网能力，共同安全模式必须拒绝，不静默扩大 Grant。未来更宽的模式须另立规格并明确告知其非等效能力。
5. **文件权限按动作配置。** Core 取得已授权 workspace 与自身必要状态的访问；Runner 默认只读源文件，并仅可写本次计划的临时/构建产物根。源码持久修改继续走 Core 的 FileMutationPlan。确需工作区写入的项目命令必须按实际路径和影响重新经过 Policy/Approval，不靠语言或可执行文件名放行。

## 命令树优先的阶段性边界

首个可实施的安全切片聚焦 **Agent 发起的 OS 命令及其后代**。Core 的 ToolExecutor 在 Policy 和 Approval 确认后，通过单一受限执行入口提交结构化命令及当次 Grant；Runner 按真实可执行文件、工作目录、只读工程根、计划产物根和网络模式创建 OS 边界。Bash、Git CLI、验证、构建、包管理器、项目脚本、Hook，以及它们派生的进程一律按同一规则进入；仅将 `ProcessSupervisor` 包一层、依靠环境变量过滤或按命令名称放行都不构成隔离。用户显式启动的外部编辑器与产品自身诊断命令须在实施计划中逐一分类，不能成为 Agent 执行项目代码的旁路。

此切片必须同时验证正常任务能运行，且命令树无法读取假 Provider Key、Core 私有状态和未授权工程，无法写入未授权路径或连接未批准网络。默认拒绝与失败关闭适用于每个 Agent 命令；后端不可用或命令无法在授权内运行时返回明确错误，不自动以无沙盒方式重试、不开例外命令清单，也不因进入沙盒而自动放宽原有 Policy 与审批。需要额外写入或联网时，先形成可审计的动作级 Grant，再重新执行；不能让项目文件或工具输出修改 Grant。

命令树切片完成时，Core 的内建 Read/Edit/Write、模型调用、Provider 凭据与恢复逻辑仍可能位于原有宿主进程。结构化状态必须分别报告 `core_isolation=none` 与 `runner_isolation=active` 等事实，并标注覆盖的命令入口；不能以单个 `OS sandbox active` 暗示完整 Core 已隔离。此状态可以作为内部研发和后续 Core 隔离的基础，不能替代本规格的完整 Core 验收或桌面前安全门禁。最终仍需由受限 Core、最小 Broker 和更窄 Runner 形成完整边界。

## 通用能力契约

Core 在执行前形成不可由项目内容伪造的 `SandboxRequest`；Policy 与用户批准产生 `SandboxGrant`。两个名称代表设计契约，字段在 ADR 与实施计划中冻结。至少包含：

- workspace identity、run/action ID、Policy 版本与指纹、批准来源、有效期和可撤销标识；
- 规范化的只读根、可写根、临时产物根、工作目录、可执行文件真实路径和必要的只读工具链资源；
- 网络模式与被批准的目的地或代理、允许传入子进程的环境变量名、进程/时间/输出资源上限；
- 当前平台后端可实际强制的能力清单，以及不能强制的项目；
- 执行结果中的后端身份、已应用能力摘要、拒绝/超时/取消原因和可恢复分类。

Grant 与精确动作及 workspace 身份绑定；路径、可执行文件、Policy 或授权事实变化时重新评估。通用项目通过每次执行发现真实工具链及资源需求，不按 Python、Node、Swift 或其他语言建立永久白名单。自动发现只能提出需求，不能自行扩大 Grant。符号链接、硬链接、挂载点、路径替换、继承文件描述符和子进程创建都必须在平台后端与 Core 边界中接受负例验证。

## 已支持平台的一致行为与实施顺序

1. **一套 Core 语义。** 同一 `SandboxRequest`、`SandboxGrant`、Policy 与 Approval 事实定义“谁、对哪个 workspace、在什么期限内可读、可写、可执行、可联网”。默认拒绝、按动作授权、Runner 比 Core 权限更窄、Provider 凭据隔离、取消与恢复失败关闭，在每个已支持平台含义相同。CLI 与桌面端都只呈现 Core 的结构化事实。
2. **不同 OS 后端，同一可见结果。** 各平台可以使用不同的进程、文件、网络和 IPC 隔离机制；后端必须报告实际强制的能力与证据。客户端展示同样的授权对象、范围、期限、状态类别和稳定错误码。平台差异不能由客户端私自解释为额外权限，也不能把应用层路径判断冒充 OS 强制。
3. **不能强制就拒绝。** 对同一请求，后端若无法施加所需的文件、网络或进程边界，应返回 `sandbox_unsupported` 或 `sandbox_unavailable`，不静默使用更宽权限、不自动退回普通宿主执行。各平台可有不同的系统授权界面，但用户最终批准的能力范围及记录格式必须一致。
4. **资源身份由各平台安全解析。** Grant 保存平台无关的资源意图与可审计身份，后端再绑定真实 OS 资源；不能把跨平台路径当作简单字符串前缀。平台进入支持范围时，验收分别覆盖 macOS 的别名/符号链接与卷边界、Linux 的链接/挂载与进程文件系统，以及 Windows 的盘符/UNC、reparse point 与大小写差异，并验证运行中替换与后代继承不会扩大授权。
5. **共同矩阵逐平台验收。** 每个拟声明支持的平台都运行同一逻辑正反例：Core/Runner 隔离、任意工程工具链、秘密与跨 workspace 拒绝、网络出口、产物根、审批过期、取消和恢复；再补各 OS 的绕过用例。源码运行、安装包及升级分别验证。评测结果使用 `Verified`、`Failed`、`Blocked`、`Not run`；未达到共同基线的平台在产品支持表中标为 `Unsupported`，不得因另一平台通过而声明支持。

一致是用户可依赖的安全承诺，不要求同一个内核技术。发布顺序为 macOS 优先、Linux 其次；Windows 仅在找到可维护且达到共同安全基线的方案时实施，也可以最终不支持。一个平台只有达到共同基线后才可标为受支持；尚未发布或已放弃的平台明确显示可用性与原因。Linux 或 Windows 的未完成验证不阻塞 macOS 的独立验收。

## 用户可见行为与失败语义

- `/status` 和结构化客户端展示 Core 与 Runner 各自的实际隔离状态、平台后端和能力限制；未验证的平台不得显示 `OS sandbox active`。
- 沙盒不可用、能力无法强制、Grant 过期、路径变化或进程试图越界时，返回稳定的 `sandbox_unavailable`、`sandbox_unsupported`、`sandbox_grant_stale` 或 `sandbox_denied` 类错误；错误说明实际副作用与下一步，不泄露秘密或不必要的私有绝对路径。
- 安全模式下不静默退回当前系统用户的普通进程。若未来提供“无沙盒执行”例外，必须另立规格、逐次取得用户对实际动作的批准，并在证据中明确记录该动作未受 OS 隔离；它不能满足本规格的验收。
- 取消、超时、崩溃和恢复不能遗留仍持 Grant 的子进程，也不能因重试重复写入、网络请求或 Git Commit。历史 Run 可以读取；恢复时若当前隔离能力不足，只允许只读检查或进入人工处理。
- Event/Journal/Receipt 只记录版本化能力摘要和结果，不记录 Provider Key、授权令牌原文、完整环境、私有文件正文或完整外发请求。
- 本规格尚未实施期间，现有 CLI 继续如实报告 `no OS sandbox` 并遵守现有 Policy；上述安全模式失败语义只在受隔离版本启用后适用。升级旧安装或恢复旧会话不能把既有非沙盒执行记录改写为沙盒证据。

## 面向开源使用者的可信证据

- 对每个宣称支持的平台与版本，公开威胁模型、默认权限、已知限制及 Core/Runner 实际隔离方式；安装包、源码运行和开发构建之间若能力不同，分别标明。
- 提供无需真实 Provider Key、私人工程或付费 API 的可复现安全矩阵，覆盖允许、审批、拒绝和失败关闭。发布证据区分 `Verified`、`Blocked` 与 `Not run`；不把静态测试或模拟器结果写成真实 OS 隔离已通过。
- 用户批准时展示此次权限的对象、范围、用途与期限；运行后可以查看授权与执行结果，并可撤销仍有效的授权。不得把安装、首次启动或信任工程解释为对未来全部命令的无限授权。
- 用户遇到拒绝或兼容问题时，应得到具体原因和可执行的下一步；修复过程不要求关闭所有安全边界。安全声明、漏洞报告与发布响应的完整流程在后续发布规格中定义，本规格不提前宣称已经具备。

## 平台实现与可行性门槛

Core 契约保持平台无关；每个平台后端必须报告可强制的文件、进程、网络和资源限制，不能靠名称宣称等效。macOS 是首发且当前唯一实施与验收优先平台，支持范围同时包含 Intel（x86_64）和 Apple Silicon（arm64）；当前 Intel macOS 开发机仅是首个参考验证环境。两个架构须分别在真实机器上验证同一 Core/Runner 安全矩阵、原生工具链、签名、独立安装与升级；仅有 Intel 实测或在 Intel 上交叉编译 arm64 不能证明 Apple Silicon 达标，Rosetta 运行结果也不能代替 arm64 原生验证。可以交付 Universal 构建或分架构构建，但每种交付形态都须独立验证。若后端随架构不同，仍须保持相同的授权与失败关闭语义。Linux 在 macOS 达到支持门槛后排第二；Windows 排第三，仅在有可维护且满足共同安全基线的方案时进入实施，若难以满足可直接放弃。平台顺序不降低任何已支持平台的共同语义或验收门槛。

macOS 后端在定型前必须用隔离原型验证：签名与启动、用户选择工程的持续授权、Core 与 Runner 的独立权限、用户安装于任意位置的可执行文件、项目自带脚本、多级构建进程、Git Hook、外部产物根和 Provider 通道。Apple 的 App Sandbox 对动态授予的可执行文件权限及复杂开发工具存在限制，不能未经实测就将其指定为通用 Coding Agent 的唯一底座。`sandbox-exec` 可作研究对照，不作为未验证的正式安全保证；虚拟化或独立系统身份等替代路径同样要满足任意原生项目的正例和全部安全负例。

若 macOS 无法同时通过通用项目执行与安全负例，macOS 后端选型及正式实施门禁保持阻断；不通过放宽定义、打包固定工具链或静默宿主执行来宣布完成。技术后端、签名/安装形式和用户选择目录的交互由后续 ADR 基于原型结果决定。

## 实施拆分与路线位置

1. **威胁与契约冻结：** 完成边界、能力字段、用户授权、执行入口清单及 Event/Journal 兼容设计。
2. **命令树后端可行性门：** 先在当前 Intel Mac 用仓库外假数据验证原生命令可用性和整棵后代进程树的文件、网络、凭据拒绝；仅在实测和发行路径成立后提出后端 ADR。既有主机改动禁令与测试延期继续有效。
3. **Runner 与工具接入：** 在另行接受规格、后端 ADR 和实施任务后，先将 Agent 发起的 Bash、Git、验证、构建、脚本与 Hook 统一接入受限 Runner；逐项排查直接调用子进程的旁路，保持 Policy/Approval/Receipt/Recovery 权威。此里程碑只可声明命令树覆盖范围。
4. **Core 与 Broker 隔离：** 再接入完整受限 Core、独立核验的资源 Broker 与 Provider 通道；Runner 保持更窄。Core 内建文件读写和其他非命令工具也须纳入最终 OS 边界。
5. **双架构与真实项目验收：** 在既定两台 Intel Mac 和 Apple Silicon 真机分别验证原生工具链、开发构建、独立安装、升级、自动对抗与 Terminal.app 真实项目。缺少 arm64 证据时可继续经授权的分阶段开发，但不能定型整个 macOS 后端或声明整体支持。

上述是规格拆分，不是实施授权或任务编号。Runner 优先修订已接受；后端选择和阶段位置仍须依据独立实测进入后续 ADR，产品实现按具体实施任务与既有阶段门禁推进。建议在阶段八、九人工验收后、阶段十桌面实施前设独立 Core 安全门禁；是否改变路线图入口条件、阶段编号和里程碑，由配套 ADR 接受后再更新。既有阶段八/九授权不能自动延伸到本规格。

## 验收标准

1. 最终验收须有操作系统证据证明整个 Core 和 Runner 分别处于声明的隔离域；Plain/JSON/TUI 对状态的展示一致。Runner 优先里程碑只按其命令树覆盖范围验收，不能满足本条完整 Core 门槛。仅通过 `ProcessSupervisor`、测试替身或文件路径检查不算通过。
2. 在没有额外 Grant 时，Core 与项目进程不能读取其他工程、用户秘密或 Vera/Broker 私有凭据，不能写工作区外任意位置；Runner 也不能读取 Core 私有状态。
3. 符号链接、硬链接、路径替换、打开的文件描述符、子进程/孙进程和 Git Hook 不能扩大文件、网络或进程权限。
4. 项目进程默认不能联网；用户批准的联网动作仅取得实际批准范围。Provider 通道只到用户配置的目的地，不向项目进程暴露凭据。
5. 用户安装在非预设路径的工具链、工程内自定义脚本和多进程构建在授予明确资源后能够完成真实任务；验证产物写入已计划的外部根，工程内额外写入按既有 Policy 处理。测试不能只覆盖预置的 Python、Node/TypeScript、Swift/Xcode 项目。
6. 拒绝、后端缺失、权限变化、取消、超时、崩溃、重启恢复与安装升级均失败关闭，有可读错误和不泄密的结构化证据；不会留下仍可执行的孤儿进程或重复副作用。
7. 在既定两台 Intel Mac 上完成开发构建与独立安装复验，并在 Apple Silicon 真机完成 arm64 原生构建、独立安装与升级复验；两个架构分别记录签名/权限、任意工具链兼容性、性能开销和安全负例。Apple Silicon 缺少实测时标为 `Not run` 或 `Blocked`，不得声明 macOS 整体已支持。未来平台逐一通过同一契约与验收后才声明支持。
8. 一个未参与开发的使用者可以按公开步骤在受支持平台复现隔离状态与主要允许/拒绝用例，看到版本对应的能力矩阵和未通过项；授权、拒绝和降级的界面文案与实际 OS 证据一致。
9. macOS 首先使用共同逻辑用例与结果分类验收；Linux 后续按同一矩阵验收，Windows 仅在决定支持时进入验收。平台特有路径、链接、进程和网络绕过另加负例。每个声明支持的平台都满足共同安全基线；未支持的平台明确报告不支持，不因客户端形态或 OS 后端改变授权语义。

## 非目标

- 本规格不引入桌面框架、Multi-Agent、插件市场或可执行 Skill，也不改变阶段八结构化 argv `bash` 的现行限制。
- 不以沙盒取代 Policy、审批、Checkpoint、Diff、验证、恢复或提示词投毒防御。
- 不要求 Linux 与 macOS 同时发布，也不承诺支持 Windows；Windows 若没有合适且可维护的安全后端，可以明确放弃。不承诺每个本机工具在首个后端中立即可用；受支持平台必须满足同一安全基线，未支持能力必须明确报告，不能伪装为隔离成功。
