# Vera 阶段五：Core 安全、权限与可靠性加固

**状态：** Draft
**日期：** 2026-09-12

## 背景

阶段一到阶段三建立了 Core、安全编辑、恢复、策略和三种 Terminal 模式；阶段四增加固定的离线评测与证据工具。完成这些工作后，Vera 已能证明冻结场景下的机制正确性，但还没有充分证明以下问题：

- 面对不同结构的真实工程，Context、工具、Diff、审批和验证能否连续稳定工作；
- 长会话、取消、进程异常、损坏状态、权限不足和磁盘错误是否会造成未批准副作用或不可恢复的数据损坏；
- 安装、升级和配置迁移是否保持安全边界；
- 真实 Provider 参与时，Core 是否仍能约束不可靠或不完整的模型输出。

因此桌面集成延后。阶段五先把 Core 打磨成安全、可靠、可独立验收的稳定基础，并冻结后续 CLI 产品化和桌面端可以依赖的边界。CLI 在本阶段是验收客户端，不是体验优化主体。

## 目标

- 对阶段四交付执行独立安全、权限、路线和文档审查，关闭全部阻断项。
- 在 Swift/Xcode、Python、Node/TypeScript 三类代表性工程副本上验证读取、搜索、普通对话、安全编辑、审批、验证、取消、恢复和回滚。
- 对文件系统、命令执行、进程生命周期、Provider 配置、私有状态和证据输出执行对抗性测试。
- 验证安装、升级、旧状态迁移、损坏状态处理和卸载后用户工程不受影响。
- 建立可重复的内部使用清单、缺陷分级和就绪报告。
- 冻结后续客户端需要的 Core Command/Event、错误、审批和恢复契约；任何客户端不得依赖 CLI 文本。

## 非目标

- 不做 TUI 视觉重构或大规模交互扩展；产品体验完善属于阶段六。
- 不实现桌面壳，不选择 Wails、Tauri、Electron 或其他桌面框架。
- 不引入 Multi-Agent、复杂 RAG、向量数据库或插件市场。
- 不承诺在阶段五公开发布，也不引入账号、计费、云端编辑或遥测平台。
- 不把 Vera 宣称为运行不可信代码的 OS 沙箱；本地命令仍以当前系统用户身份运行。
- 不通过放宽 Workspace、PolicyEngine、审批或命令策略来提高任务成功率。
- 不在自动测试、CI 或 Agent 审查中读取真实 DeepSeek/GLM Key。

## 阶段入口条件

阶段五只有在以下条件满足后开始：

1. 阶段四任务 0015–0019 已提交并本地合并到干净 `main`；
2. 阶段四 14 条退出条件有对应证据；
3. 独立审查没有未处理的安全、权限、路线或文档阻断项；
4. 完整非 live 门禁通过，真实 Key 未暴露给自动测试或审查 Agent。

入口审查发现的问题属于阶段四返工，不得通过阶段五任务掩盖。

## 验收客户端边界

阶段五继续保留四个平级 Core 客户端：

```text
Vera Core Command/Event
    ├── vera                 # 默认 Textual TUI
    ├── vera --plain         # 稳定纯文本交互
    ├── vera --json          # 机器可读 Session
    └── vera eval            # 离线评测客户端
```

阶段五只在 CLI 错误展示会掩盖真实状态或安全边界时做必要修复。补全、输入体验、视觉层次、主题、帮助系统和产品化细节统一留给阶段六，避免与 Core 加固混杂。任何修复都不得把业务判断放进 Presenter，也不得增加只对 TUI 生效的 Runtime 分支。

## 审查与风险分级

阶段五使用以下分级：

| 等级 | 定义 | 阶段五完成要求 |
|---|---|---|
| `Critical` | 未批准命令/写入、工作区逃逸、凭据泄漏或大范围不可恢复破坏 | 必须修复并增加回归测试 |
| `High` | 审批绕过、错误恢复导致数据不一致、私有证据泄漏或稳定复现的严重权限错误 | 必须修复并增加回归测试 |
| `Medium` | 有安全降级但存在明确人工恢复路径，或主要流程高频失败 | 必须有修复或明确接受记录 |
| `Low` | 不影响边界和数据完整性的体验、诊断或性能问题 | 可以带入后续阶段，但必须记录 |

任何 `Critical` 或 `High` 未关闭时，阶段五不能完成。

## 安全与权限加固

### 文件系统

- 所有工具、Change Set、Checkpoint、恢复和评测输出都必须保持 workspace 边界。
- 覆盖 `..`、绝对路径、Unicode/大小写差异、符号链接替换、FIFO、Socket、设备文件和检查后替换竞态。
- 写入前重新确认目标事实；批准后目标或基线变化时使旧审批失效。
- 临时目录、私有状态和证据目录保持最小权限，不覆盖既有路径，不跟随不可信链接。

### 命令与进程

- 命令始终使用结构化 argv 和 `shell=False`，cwd 必须位于批准工作区。
- PolicyEngine 对禁止、需批准和允许命令保持单一权威；Presenter 不得覆盖决策。
- 验证取消、TERM→kill、超时、子进程退出、超大 stdout/stderr 和孤儿进程清理。
- 子进程环境采用明确 allowlist，不能继承无关 Provider Key、认证 Token 或 Agent 私有变量。

### 审批

- 审批必须绑定规范化动作、参数、工作区、策略 hash 和当前事实，不接受模糊的“批准后续全部操作”。
- 重复、过期、未知或跨 run 的 approval ID 必须失败关闭。
- 恢复、回滚、验证命令和文件写入继续使用各自明确的审批类型。
- 用户拒绝或取消后不得产生被拒绝的副作用，也不得静默重试成另一个等价动作。

### 凭据、日志与证据

- Provider Key 只由用户本地进程读取，不进入 Event、错误、日志、Snapshot、Checkpoint、证据包或测试夹具。
- 对 Authorization、Bearer、常见供应商变量和高熵 Token 进行结构化脱敏测试。
- JSON/Plain/TUI 的错误输出不能包含请求正文、环境快照或用户文件正文。
- 阶段五自动门禁必须在清除供应商变量并阻止网络的环境中通过。

## 可靠性与数据完整性

- 覆盖运行前、等待审批、部分写入、验证中、验证后、回滚中和 Journal 写入中的中断。
- 重启后只根据持久事实分类；不依赖旧进程内存、Stream Frame 或终端文本。
- Snapshot/Journal/Checkpoint 损坏、未知版本和不完整尾记录必须失败关闭并提供可执行的人工处理建议。
- 空间不足、只读目录、文件占用、编码错误和验证程序异常不能导致成功假象。
- 同一 Resume、ResolveApproval、Cancel 或 Rollback 重放不得重复副作用。
- 长会话必须限制上下文、日志、Event 和终端内存增长，并能安全取消当前 run。

## 代表性工程内测

自动测试使用仓库内最小夹具或临时生成的工程形状；人工内测只能在用户明确选择的工程副本上运行：

| 工程类型 | 最少覆盖 |
|---|---|
| Swift/Xcode | 项目目录发现、Swift 文件读取/修改、Diff、用户批准的本地验证 |
| Python | 包结构、pytest/静态检查、创建与多文件修改、失败回滚 |
| Node/TypeScript | package scripts 发现、源文件修改、lint/test、命令审批 |

每类工程必须覆盖：只读理解、普通对话、单文件修改、多文件修改、拒绝审批、验证失败、取消、恢复和回滚。自动夹具证明确定性；真实工程人工记录证明可用性，两者不能互相替代。

用户可以选择执行低预算真实 Provider smoke，但必须满足：

- 由用户本人设置和持有 Key，审查 Agent 不读取 Key；
- 不把 live 测试加入默认 pytest 或离线评测；
- 只记录供应商、模型、结果类型、用量和脱敏错误，不记录 Key 或完整请求；
- live 失败不通过修改安全策略来规避。

## 安装、升级与兼容

- 从本地 wheel 在仓库外临时环境安装后，四种 CLI 入口均能启动。
- 从上一已封存版本升级时，配置和私有状态要么完成版本化迁移，要么明确拒绝并保留原始数据。
- 重复安装、缺失配置、不可写 state 目录和未知 schema 有稳定错误与退出码。
- 安装、升级或卸载不能修改用户工程；临时验证产物必须可明确识别和清理。
- Python 和操作系统支持范围必须记录，Intel macOS 的实际支持状态不能由开发机单次成功推断。

## 内部稳定性记录

阶段五建立一份可审阅的 dogfood 记录，至少包含 20 次连续内部任务，覆盖三类代表性工程和全部关键工作流。记录只保存任务类别、结果、失败分类、恢复方式和脱敏指标，不保存用户源文件正文或模型秘密。

以下情况会中断“连续稳定”计数并成为阻断问题：

- 未批准写入或命令执行；
- workspace 逃逸或秘密进入日志/证据；
- Vera 导致且无法从 Checkpoint/备份恢复的数据损坏；
- 将失败、取消或未验证结果错误标记为成功。

普通模型拒答、用户拒绝审批或被策略正确阻止不算 Core 稳定性失败，但必须分类记录。

## 文档与契约冻结

- 规格、ADR、任务、代码、测试、CLI 帮助和验收证据必须描述同一行为。
- 公共 Command/Event、错误码、审批类型、恢复分类和 JSON 输出的变更必须版本化。
- 删除或改变已接受字段必须提供兼容策略，不能让后续 CLI 或桌面端依赖未记录的内部细节。
- 阶段完成报告必须区分：自动验证、用户人工验证、未验证假设和已接受限制。

## 失败行为

- 安全或权限审查出现 `Critical`/`High`：阶段阻断，先修复并重新审查。
- 真实工程暴露规格缺口：先回到规格/ADR，不用临时分支绕过 Core 边界。
- live Provider 不可用：保留离线门禁结果，记录为人工验证受阻，不暴露或更换用户 Key。
- 安装或迁移失败：保留原状态和证据，不自动删除或重建用户数据。
- 文档与代码冲突：以已接受规格/ADR 为准；无法判断时停止实施并请求决策。

## 阶段退出条件

只有同时满足以下条件，阶段五才算完成：

1. 阶段四独立审查完成，安全、权限、路线和文档阻断项全部关闭；
2. 所有 workspace 逃逸、符号链接/特殊文件和检查后替换负例通过；
3. 命令策略、环境 allowlist、超时、取消和子进程清理负例通过；
4. 审批绑定、过期审批、跨 run 审批和拒绝零副作用通过；
5. Key、Token、请求正文和用户文件正文不进入日志、状态或证据；
6. 所有已支持恢复阶段有中断测试，重复恢复命令保持幂等；
7. 损坏/未知状态、磁盘和权限错误失败关闭，不出现虚假成功；
8. Swift/Xcode、Python、Node/TypeScript 三类工程完成规定工作流验收；
9. 至少 20 次连续内部任务没有未批准副作用、边界逃逸、不可恢复损坏或虚假成功；
10. 本地 wheel 的全新安装、上一版本升级、仓库外启动和错误配置路径通过；
11. 默认 TUI、`--plain`、`--json`、`vera eval` 继续共享 Core 契约；
12. 公共协议和兼容承诺有版本化文档，桌面客户端不需要解析 CLI 文本；
13. 没有未关闭的 `Critical` 或 `High`，`Medium` 均有明确处置记录；
14. 完整非 live 测试、Ruff、格式、Mypy、构建、wheel smoke 和 `git diff --check` 通过；
15. 自动验收未读取真实 Key、未修改未授权用户工程、未引入桌面框架。

满足这些条件后，才能进入阶段六 CLI 产品化与体验完善。
