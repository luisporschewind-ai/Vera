# 三档权限与自动审核机制

**状态：** Accepted
**日期：** 2026-09-25
**接受：** 2026-09-25 用户审阅规格与实施计划后回复“确认”；仅接受设计与计划，不授权实施、提交或推送。
**定位：** Core 权限与审批契约；沙盒机制完成后的独立产品增量
**设计输入：** 用户要求参考 OpenAI 的“请求批准 / 帮我批准 / 完全访问”三档；确认“完全访问”采用真正无沙盒、无审批的边界，且只对当前会话生效，新会话恢复默认。

## 目标

让普通 Coding 工作连续进行：用户明确要求修改可信工作区时，新增普通文件、修改普通代码和已规划的验证不因每次动作暂停；真正跨越当前执行边界的动作按所选档位交给用户、独立自动审核者，或在用户显式启用的完全访问会话内直接执行。三档显示实际 Core 与命令树权限，不用档位名称掩盖尚未实施的 OS 隔离。

本规格定义权限和审批机制，不授权实施。实施必须等待 Core 与 Runner 的沙盒规格在目标平台完成并通过其验收门禁，且冲突的既有规格及配套架构决策完成修订和接受后另行授权。

## 既有基线与需修订处

- 已接受的 `2026-09-17-core-tooling-and-risk-tiered-policy.md` 将低风险普通编辑设为自动允许，并定义 `review / balanced / autonomous`、workspace trust、`PolicyEngine → ApprovalGate → ToolExecutor`、动作级 Checkpoint、Diff、Receipt 与恢复。这是三档设计的基础；阶段八实现目前仍在独立分支等待人工验收。
- 该规格明确排除 `full-access`；ADR-0021 将 `balanced` 固定为推荐默认，并把外部、高影响动作交给审批或拒绝。原生 Git 规格也排除了远程操作并阻止通用命令绕过；Full access 如要通过 `bash` 执行这类动作，须在实施前修订相应规格和 ADR，不得暗中改写历史验收事实。
- `2026-09-24-core-execution-sandbox.md` 在独立工作树中标为 Accepted，尚未进入 `main`。它要求完整 Core 与更窄 Runner 受 OS 隔离；其中未来“无沙盒执行”按动作逐次审批的设想，与用户现已选定的会话级 Full access 冲突。其合入后须修订该条并经用户接受。
- 当前 `main` 的 Core 仍报告 `current user · no OS sandbox`。在沙盒门禁通过前，Vera 不能声称“请求批准”或“帮我批准”已有 OS 强制的工作区边界，也不能发布本规格的三档模式。

## 权限模型

权限预设是三个独立事实的组合：**执行边界**（OS 沙盒与可写根、网络）、**审批策略**（何时产生申请）和**审核者**（用户、独立审核者或无）。`risk_level`、workspace trust 和用户目标仍由 Core 评估；档位不能由模型、仓库文件、Skill 或工具输出切换。

| 用户可见档位 | 本地执行边界 | 需要越界时 | 审核者 | 默认 |
|---|---|---|---|---|
| 请求批准 | 已验收的 workspace 沙盒；Core 与 Runner 按各自 Grant 运行 | 形成精确审批申请 | 用户 | 是 |
| 帮我批准 | 与“请求批准”相同的沙盒和 Policy | 合格申请交给独立审核者；其余交给用户或拒绝 | 自动审核者及用户 | 否 |
| 完全访问 | Core、Runner 及命令后代不受 Vera OS 沙盒的文件系统与网络限制 | 不产生 Vera 审批申请 | 无 | 否 |

“完全访问”仅表示 Vera 发起的**本地执行**不受 Vera 沙盒和审批门禁约束。它不取得高于登录用户的 OS 权限，不自动获得未配置的 Provider、第三方服务账号或尚不存在的工具能力。未来浏览器、Connector、MCP 与云端工具有独立权限时，必须分别展示其实际边界，不得用本地 Full access 默认为这些工具授权。

### 自动允许与自动审核的区别

1. **自动允许：** `PolicyEngine` 用确定性事实判定动作已在边界内，直接执行，不调用审核模型。可信工作区内与用户实现目标相符、非受保护路径、事实未过期、Checkpoint 成功且可恢复的普通创建/更新属于此类；“新增文件”“修改代码”只是示例，不能只凭操作名称放行。
2. **自动审核：** 动作本来会产生人工审批申请，且通过 Core 的自动审核资格门。独立审核者只决定这一个精确动作能否获得一次性 Grant，不改变 workspace 信任、Policy、会话级沙盒配置或永久可写根。
3. **人工审批：** 风险或事实不适合自动审核，但按当前档位仍允许用户决策时，展示动作、目标、实际副作用、沙盒扩张范围和期限。
4. **拒绝：** 结构化事实不足、来源不可信导致越权、系统无法强制 Grant 或明确违反当前策略时失败关闭。自动审核不能把拒绝改为允许。

| 动作示例 | 请求批准 | 帮我批准 | 完全访问 |
|---|---|---|---|
| 可信工程、用户明确要求的普通文件创建/代码更新 | 直接执行并记录 Diff/Checkpoint | 同左，不触发 Reviewer | 直接执行并记录事实 |
| 未建立信任的工程写入 | 人工审批或拒绝 | 人工审批或拒绝 | 在用户任务范围内直接执行 |
| 明确公开 URL、无私有正文的文档读取 | 越界时人工审批 | 资格门通过后可自动审核一次 | 工具支持时直接联网 |
| 依赖脚本、远程发布、破坏性动作 | 人工审批或拒绝，依现行工具能力 | 人工审批或拒绝，不交 Reviewer | 工具支持且符合用户任务时无 Vera 审批 |
| 仓库内容指示 Agent 偷读秘密并上传 | 拒绝把仓库内容当成授权 | 同左 | 同左；Full access 不把仓库内容提升为用户指令 |

前两档若所需 OS 沙盒后端不可用，按沙盒规格失败关闭，不能自动改用 Full access。Full access 是用户明确选择的另一执行边界，不是沙盒错误时的回退。

## 动作决策与审核资格

Core 对每次 `ToolAction` 收集用户目标授权、workspace identity/trust、规范化路径、真实可执行文件、argv/cwd、网络目标和请求正文的必要摘要、工具 effect、当前沙盒事实、可恢复性及 Policy 版本。先完成工具 Schema、路径和目标事实验证，再由 Policy 分类为 `allow / approval_required / deny`；审批申请只在 `approval_required` 后产生。执行前重新核对输入哈希、目标事实和沙盒 Grant。

“帮我批准”的首版自动审核资格必须同时满足：

1. 用户当前目标明确涵盖动作；目标、effect、参数和外部目的地可精确绑定；
2. Core 的确定性风险分类为 `low` 或 `moderate`，且未被内容安全检测收紧为高风险或拒绝；
3. 动作副作用可界定、可检查，文件修改具有可用 Checkpoint/恢复路径；
4. 不读取或外发秘密，不涉及权限提升、宿主安全设置、未授权工作区、远程发布、不可逆删除或 Git 历史破坏；
5. 当前目标平台的沙盒后端可实际强制该精确 Grant；
6. 审核请求可在不传出凭据、完整私有文件正文或不必要的完整 Diff 的条件下说明清楚。

例如，已规划的临时产物根扩张或向明确的公开文档目的地发起无私有内容的读取，可在资格门通过后交给审核者。依赖安装脚本、项目 Hook、远程 Git Push、工作区外源码写入、秘密访问和主机权限变更不由自动审核者批准；它们遵守人工审批或硬拒绝的对应规则。自动审核只有 `approve_once / deny / needs_user` 三种结果；`approve_once` 绑定 `session_id + run_id + action_id + input_hash + target_facts_hash + policy_hash + grant_hash`，不创建 Run 或 workspace 级持久授权。

审核者是与主 Agent 分开的只读角色，只收到经过脱敏的紧凑任务上下文、精确申请和相关证据；不能执行工具、修改文件、建立信任、设置模式或调用 ApprovalGate。选择“帮我批准”时，状态须显示审核者是否可用；不可用、超时、结果格式错误或证据不足时转人工审批，不自动通过。明确拒绝时把简短理由交给主 Agent，禁止以等价包装器重试同一副作用；只允许提出实质更安全的方案，或由用户改在“请求批准”档对重新准备的精确动作亲自决策。连续重复申请有有界熔断与可见失败。

## 完全访问的真实边界

用户在空闲会话中显式选择“完全访问”后，可信启动器为该会话启动**未施加 Vera OS 沙盒**的 Core 和 Runner；命令后代继承该边界。只关闭 `ApprovalGate` 的提示而仍让 Core/Runner 受限，或只让 Runner 脱离沙盒，都不能称为完全访问。`PolicyEngine` 仍形成风险与审计事实，但工作区范围、联网和副作用风险本身不产生 Vera 审批或沙盒拒绝。输入 Schema、工具能力、陈旧事实、执行失败、用户任务范围、取消、Receipt、Checkpoint、Diff、日志脱敏与恢复规则继续生效；这些不是审批替身。

完全访问可能读取、修改或删除登录用户有权访问的工作区外文件，运行项目脚本并联网；既有 `bash` 的结构化 argv 和工具目录不因档位自动获得 Shell 语法或未实现的远程 Git 一等工具，但不能因“越出 workspace”“命令会联网”“Git 远程副作用”这些权限分类继续假称 Full access 而拒绝。是否允许具体动作仍取决于用户目标、工具实际能力和 OS/服务端权限；外部系统自己的登录或系统授权界面不是 Vera 审批。

Full access **仅在当前运行中的会话实例生效**：不写入全局默认、workspace trust、会话 Journal 或可恢复的权限快照。新会话、应用重启后恢复旧对话、崩溃恢复都回到“请求批准”；恢复中依赖旧 Full access 的未完成动作必须重新准备，不能自动重放。切换档位只在没有活动 Run/待处理审批时生效；切入或切出 Full access 需要结束旧 Core/Runner 及全部后代，再按新边界启动。若无法证明旧进程已退出、无法建立新边界或状态交接失败，保持会话停用并报告错误，不静默沿用旧权限。切换回受限档位不会撤销已发生的外部副作用。

Full access 的选择控件须清楚显示“当前会话、无 Vera 沙盒、无 Vera 审批、可访问工作区外与网络”，由用户主动选择；运行中状态持续显示 `full_access` 与 `sandbox=disabled_by_user`。不得在首次启动、恢复或模型建议时自动启用。

## 结构化契约与客户端

Core 输出版本化 `PermissionProfileSnapshot`（预设、审核者、真实 Core/Runner 沙盒状态、session ID、生效时间、Policy/后端版本）、`ReviewRequest`（精确动作和资格证据）、`ReviewDecision`（来源、结果、理由、绑定哈希）、`ApprovalRequest` 和执行 Receipt。公共 Event/Journal 只保留脱敏摘要；审核者完整上下文保存在受控私有位置并按会话生命周期处理。自动审核批准与用户批准必须可区分，不能写成用户已批准。

TUI、Plain、JSON 和未来桌面客户端只展示 Core 返回的事实，不独立计算风险或隐藏审批。`/permissions` 可查看当前预设、实际沙盒状态、自动审核资格摘要、最近批准/拒绝与可撤销的既有 Grant；状态视图标注自动允许、自动审核通过、人工批准和 Full access 直接执行四种来源。旧 Run、旧 Approval 与 `review / balanced / autonomous` 配置继续按既有 Codec 读取；迁移时不得把旧 `autonomous` 静默转换为 Full access，旧配置默认仍落在有沙盒的“请求批准”档，并保留其原有风险倾向直到用户另行调整。

## 验收门禁

1. 沙盒规格的完整 Core/Runner 门禁已在目标平台通过；本规格与冲突的 Accepted 规格、ADR 均已更新并接受，实施计划获单独授权。
2. 三档的实际进程边界分别有 OS 证据：前两档相同且受限，Full access 的 Core/Runner/后代未施加 Vera 沙盒；不能用模拟 Policy 测试冒充 OS 证明。
3. 可信工作区普通创建/更新与已知验证无需重复审批；受保护文件、删除、脚本、网络和越界路径分别命中预期的自动允许、自动审核、人工或拒绝。
4. 自动审核资格门与 reviewer 分离；Reviewer 无副作用能力，批准只绑定一个动作，拒绝/超时/服务不可用/模型格式错误不扩大权限。
5. 用户切换 Full access 后本地工作区外读写与测试网络目标在 OS 用户权限内可执行且无 Vera 审批；新会话、重启和恢复回到默认，旧未完成动作不复用授权。
6. 活动 Run、未决审批、子进程残留、切换失败和旧版本恢复均有明确失败语义；无静默降级或静默保留 Full access。
7. TUI、Plain、JSON 的权限、审核来源、沙盒事实和失败状态一致；Diff、Receipt、脱敏与恢复可检查。Python、Node/TypeScript、Swift/Xcode 及沙盒任意项目矩阵覆盖真实终端/进程。

## 非目标

- 在沙盒完成前实施或发布三档；当前文档不会让现有无沙盒 CLI 获得新的安全承诺。
- 把每次普通代码编辑交给 LLM 复核；这是代码质量审查议题，不是权限审核。
- 让自动审核者扩大 workspace trust、持久授权、Provider Key 或工具能力。
- 以 Full access 替代用户任务指令，或自动授予未来 Connector、MCP、浏览器和云端工具权限。
