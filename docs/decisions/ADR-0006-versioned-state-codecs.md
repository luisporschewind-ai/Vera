# ADR-0006：版本化 Codec 与非破坏迁移

**状态：** Proposed
**日期：** 2026-09-11

## 背景

当前 Command、Event 和多数持久化对象都使用 `schema_version=1`，但读取逻辑直接依赖当前 Pydantic 模型。恢复快照引入后，如果公共协议、Journal 编码和快照格式共用一个版本，任何局部演进都会造成不必要的整体迁移。

## 决策

- 分离 `schema_version`、`journal_format_version` 和 `snapshot_version`；产品版本只用于诊断。
- 在边界建立 `ContractCodec` 与 `StateCodec`，由版本注册表选择 Decoder 和纯迁移函数。
- 已知旧格式迁移到当前内存模型；未知未来版本返回 `unsupported_version` 并停止写回。
- Event Journal 保持追加写入，不因迁移原地重写、重排或删除。
- 阶段一没有恢复快照的 run 保持可查看和安全回滚，但标记为 `legacy_not_resumable`。
- 只有只读 Decoder 无法满足需要时才执行磁盘迁移；迁移必须提供 dry-run、恢复副本、原子写入和结果校验。
- 阶段二建立迁移能力，但不为了展示能力而随意升级公共协议版本。

## 备选方案

### 直接让每个 Pydantic 模型兼容所有版本

版本判断会散布到业务模块，难以确认迁移路径和删除旧兼容代码，因此不采用。

### 启动时自动原地升级全部状态

可能破坏唯一历史证据，也使新版本无法安全回退，因此不采用。

### 用 Vera 产品版本推断数据结构

产品发布和多类数据格式不会同步演进，推断不可靠，因此不采用。

## 后果

- 数据演进入口集中，冻结 Fixture 可以覆盖真实兼容矩阵。
- 旧 run 不会被伪装成具备原本不存在的恢复能力。
- Codec 和迁移注册表增加少量结构，但避免未来在 Runtime 中堆叠版本条件。

## 验证与重审触发器

- 固定当前版本、已知旧版本、未知未来版本和损坏数据 Fixture。
- 验证迁移失败不会改变原 Journal 或快照。
- 当需要删除某个旧 Decoder 时，必须先定义支持周期和用户可执行的迁移路径。
