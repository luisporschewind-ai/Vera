# ADR-0017：插入 CLI 体验阶段并顺延桌面路线

**状态：** Accepted
**日期：** 2026-09-13

> 后续关系：[ADR-0020](ADR-0020-stage-core-native-skills.md) 与 [ADR-0021](ADR-0021-core-tools-before-desktop.md) 依次在桌面前插入 Skills 及工具/Policy/Git 阶段；[ADR-0023](ADR-0023-insert-core-observability-before-desktop.md) 再将 Core Trace 插入桌面之前。当前桌面为阶段十一、私有预览与公开准备为阶段十二。本 ADR 下文中的“阶段八桌面、阶段九公开准备”保留为 2026-09-13 接受时的历史事实；阶段七边界与精确封存门禁继续有效。

## 背景

阶段六已经完成大部分 CLI 功能、可靠性、终端兼容和自动产品验收，但真实 dogfood 表明，“功能可用”与“愿意长期作为个人主力工具使用”之间仍有明显差距。当前路线把 Logo、启动首屏、视觉层级、主题收口和持续个人体验混在阶段六的通用产品化条款里，没有形成独立阶段和实施任务；原阶段七则已经明确用于桌面 Agent 工作台。

继续把视觉与体验工作塞进阶段六，会模糊已完成的功能基线；使用“阶段 6.5”可以减少编号修改，却会让完成状态、进入条件和封存门禁出现歧义。桌面实现尚未开始，此时顺延编号的迁移成本可控。

路线图是根据新证据持续校准风险和交付顺序的工具，不是接受后便不可调整的冻结承诺。当前真实使用已经证明，先提高 Core/CLI 的稳定性、连续性和产品体验，比尽快产出一个初步桌面专案更重要；将桌面阶段后移是在降低返工和集成风险，而不是改变 Vera 最终作为桌面 Agent 的方向。

## 决策

- 阶段六收口为“CLI 功能与可靠性”，保留任务 0025–0033，并纳入走查后新增的任务 0042；其功能、错误保真、终端兼容、工作区无污染和自动验证事实继续有效。
- 在桌面阶段前新增“阶段七——CLI 体验收口与个人主力化”。持久化对话会话、TUI 视觉识别、启动首屏、布局层级、主题、交互细节和持续个人 dogfood 在该阶段实施。
- 原“阶段七——桌面集成”顺延为阶段八；Electron 仍是首个桌面底版，技术选择本身不变。
- 原“阶段八——私有预览与公开准备”顺延为阶段九。
- 用户确认「CLI 版本达到预期，可以封存」的最终门禁从阶段六退出条件移动到阶段七退出条件。
- 阶段六可以在既有功能与可靠性门禁、当前修正任务和相应验证完成后关闭，但关闭阶段六不授权任何桌面工作。
- 未经用户原文确认「CLI 版本达到预期，可以封存」，不得把阶段七标为 Complete，不得开始阶段八，也不得添加 Electron、Tauri、Wails 或其他桌面端代码、依赖与技术 Spike。
- 已完成任务、评测报告和 Git 历史中的旧阶段编号作为当时证据保留；仍在生效的路线图、规格、决策、任务入口与协作规则更新为新编号。

## 阶段边界

| 阶段 | 主要回答的问题 | 退出证据 |
|---|---|---|
| 阶段六 | CLI 的功能、错误、终端行为、工作区无污染和可靠性是否成立 | 任务 0025–0033、任务 0042、自动门禁和必要的缺陷复验完成，无未关闭的 Critical/High 正确性或可靠性问题 |
| 阶段七 | CLI 是否在视觉、交互、连续性和长期 dogfood 上达到个人主力标准 | 真实 Terminal.app 与真实工程持续使用通过，用户明确确认可以封存 |
| 阶段八 | 桌面客户端是否能安全复用 Core 完成 Agent 工作台闭环 | Electron 客户端完成结构化 Core 工作流并通过桌面安全、性能和打包门禁 |
| 阶段九 | 产品是否适合可信用户预览与后续公开准备 | 发布检查清单、安全与供应链门禁完成 |

正确性缺陷不因发生在 TUI 就自动归入阶段七：用户消息缺失、工具事实错误、审批误导、终端损坏等仍属于阶段六可靠性问题。Logo、配色、信息密度、视觉层级、品牌一致性和主观使用质感属于阶段七。

## 后果

- 路线图能明确区分“能可靠工作”和“达到个人主力产品体验”，避免用自动测试代替使用判断。
- 阶段七获得独立规格、任务顺序和真实使用门禁，TUI 视觉不再作为零散修正夹带在缺陷任务中。
- 桌面与私有预览的编号整体顺延，需要校准现行文档中的交叉引用；历史验收记录不重写。
- 持久化会话规格的实现阶段改为阶段七，但其 UI 无关 Core、Session Journal 与 Run Journal 分离等技术决策不变。
- 桌面 Logo 与应用图标在阶段八继续扩展，但必须继承阶段七确认的 Vera 识别方向，不能另起一套不一致的品牌语言。

## 被拒绝的方案

- **继续全部留在阶段六：** 改动最少，但功能基线、视觉重构、长期 dogfood 和最终封存继续混在一个阶段，无法说明当前到底完成了什么。
- **新增阶段 6.5：** 能表达插入顺序，但会让阶段六是否完成、封存门禁属于哪一层以及后续引用方式长期含糊。
- **把 TUI 视觉放入桌面阶段：** TUI 是当前真实产品表面，等待桌面阶段才处理会阻止 CLI 达到个人主力标准，也会让桌面工作反向承担 CLI 债务。

## 与现有决策的关系

- 本 ADR 取代 [ADR-0012](ADR-0012-delay-desktop-until-cli-hardening.md) 中“桌面集成为阶段七”和“CLI 最终封存属于阶段六”的编号与门禁归属；其 Core-first、CLI-first、桌面延后原则继续有效。
- 本 ADR 只校准 [ADR-0013](ADR-0013-electron-desktop-baseline.md) 的实施阶段编号为阶段八；Electron、Python Core 和结构化 Command/Event 边界不变。
- [ADR-0016](ADR-0016-persistent-conversation-sessions.md) 的持久化架构不变，实施归属由阶段六移动到阶段七。
